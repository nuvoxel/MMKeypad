# Control4 intercom / FreeSWITCH — how it works (and where our keypad fits)

How the intercom on the dev EA-3 (`ea3-<director-serial>` @ 192.168.1.220) is wired,
what our keypad does inside it, and options for a UniFi Talk bridge. Inspect it
live with `fs_cli` on the Director (see "Poking at it" below). Access via
our internal Director-access notes (not published).

## The shape of it

Control4 intercom = **FreeSWITCH** (SIP + media) with the **Director as its
brain**. FreeSWITCH itself holds almost no static config; everything is resolved
live.

```
 keypads / door stations / UniFi Access / mobile app   (SIP endpoints, LAN)
        │  register + INVITE (SIP/TCP or TLS)
        ▼
   FreeSWITCH  /opt/freeswitch   (PID 12092)
   ├─ profile internal  :5060 (UDP/TCP) + :5061 (TLS)   ← all LAN endpoints register here
   ├─ profile external  :5080 + :5081 (TLS)
   │   └─ gateway external::ia-trunk → REGED to intercom.control4.com:5081
   │        (Control4's CLOUD intercom relay — off-LAN / 4Sight / app-away-from-home)
   ├─ mod_conference     ← all-call / announce is a conference bridge
   ├─ mod_sofia, mod_dptools (page/presence), mod_opus, mod_event_socket :8021
   └─ mod_xml_curl  ───────────────┐  every directory/dialplan/configuration lookup
        gateway-url:               ▼
        http://<director>:8095  =  the **director** process (PID 11886) answers
        bindings="dialplan|directory|configuration"   (2 retries, same URL)
```

**Key point:** FreeSWITCH asks the Director, over HTTP on `:8095`, for
- **directory** — "is this user allowed to register, and what's their auth?"
- **dialplan** — "I got a call to X, what do I do with it?" (incl. all-call routing)
- **configuration** — profile/module config

So the Director decides who can register, how calls route, and who an announcement
reaches. `/opt/freeswitch/conf` is empty on disk for exactly this reason; the real,
dynamic config comes from the Director.

## Registration

Endpoints register to the **internal** profile, realm `192.168.1.220`. The
Director's directory response returns a per-user `a1-hash` (SIP digest auth) and a
`dial-string` built from `sofia_contact` (so a call to a user reaches its currently
registered contact). Verified live — our keypads register fine:

```
show registrations →
  MMKeypad_3333  sip:MMKeypad_3333@192.168.70.49  tcp   REGED   (Guest Room)
  MMKeypad_3342  sip:MMKeypad_3342@192.168.223.232 tcp  REGED   (Bedroom)
  C4DS2-54-…     …  tls   (native door stations)
  UniFi_3050_cpvu …  tcp   (UniFi Access door, via Chowmain driver)
```

- **SIP username = `MMKeypad_<c4DeviceId>`.** It is keyed to the Control4 project
  device id, so deleting/re-adding a keypad changes its SIP identity (old
  registrations linger until they expire). This is why churn in the agent (see
  [mmkeypad-agent-dedup]) leaves stale `MMKeypad_NNNN` regs for a while.
- Codecs on internal: `H264, OPUS, G722, PCMU, PCMA, GSM` (H264 for door-station
  video; OPUS/G722 for audio).

Our side of registration: the per-device keypad driver's `intercom.lua`
(`PushSipConfig`) provisions the SIP account params down the :6700 link; the
firmware SIP UA (`firmware-idf/main/sip.c`) does the actual REGISTER. The proxy
sub-binding (5003) carries call/level state to Control4.

## All-call / announce

There is **no persistent static "all" group** in FreeSWITCH. An announcement is a
**conference** the Director orchestrates: on all-call it originates to each
**announce-capable** endpoint and bridges them into a `mod_conference` room. The
target set is computed by the Director from the project's intercom devices.

Consequences (matching what you observed):
- **All-call does not ring door stations** — correct: door stations are call
  *sources* (entry points), not announce *targets*.
- Whether a keypad is an announce target is the Director's call, from the device's
  intercom classification — not a group the endpoint "joins" itself.

**Status of our keypad in all-call: NOT yet confirmed.** Registration is healthy,
but confirming it's an announce *target* needs a live test — trigger an all-call
and watch for an INVITE to `MMKeypad_<id>` (fs_cli `sofia global siptrace on`, or
watch `show channels`). TODO.

## UniFi Talk integration (future)

UniFi Talk is a separate SIP PBX. Two models:

1. **SIP trunk (realistic).** Bridge the two PBXs with a trunk, mirroring the
   existing `external::ia-trunk` gateway pattern (an external-profile gateway to a
   SIP peer). C4 all-call → route over the trunk → a UniFi Talk ring group, and
   vice-versa.
2. **Register UniFi phones as C4 endpoints (not realistic).** UniFi phones are
   managed by UniFi Talk and won't cleanly register to a foreign PBX.

**The hard constraint:** Control4's FreeSWITCH is a locked appliance whose config
is generated by the Director via xml_curl (`:8095`) — you cannot just add a static
gateway; the Director would need to know about it, and it's Control4's to control.
So the practical shape is a **small SBC/bridge you own** (a container/Pi running
FreeSWITCH or Asterisk) that:
- registers/trunks to **UniFi Talk** on one side, and
- registers to Control4's **internal** profile as an endpoint (or trunks to the
  external profile) on the other,
- and maps C4 intercom all-call ↔ a UniFi Talk ring group.

Since our keypad firmware owns its SIP UA, an alternative worth prototyping: have
the keypad *also* reach UniFi Talk directly — but per-device dual-registration is
messier than one bridge. The bridge/SBC is the cleaner architecture.

## Poking at it (fs_cli)

```sh
FS=/opt/freeswitch/bin/fs_cli
$FS -x "sofia status"                       # profiles + gateways
$FS -x "show registrations"                 # who's registered
$FS -x "sofia status gateway external::ia-trunk"   # cloud relay health
$FS -x "conference list summary"            # active announcements
$FS -x "sofia global siptrace on"           # live SIP trace (then watch the log)
# directory lookup the Director returns for a user (auth/a1-hash):
curl -s http://127.0.0.1:8095 --data-urlencode section=directory \
  --data-urlencode key_name=name --data-urlencode key_value=192.168.1.220 \
  --data-urlencode user=MMKeypad_3333 --data-urlencode domain=192.168.1.220 \
  --data-urlencode action=sip_auth
```
